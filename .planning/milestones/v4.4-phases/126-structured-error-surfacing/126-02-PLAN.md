<objective>
Close ERR-03: storage save failures become observable via a shared `onPersistenceError` hook + `lastPersistenceError` status + a queryable `persistenceHealthy` health flag, symmetric across both hosts, and stop being misclassified as AI failures.

Purpose: Three inconsistent storage paths exist today — `create()` is fire-and-forget `.catch(console.error)`, `#save()` has NO catch (throws propagate / unhandled rejection), and `#checkAITurn` calls `#save()` INSIDE the AI try/catch so a storage outage increments `#aiConsecutiveFailures` and logs a misleading "[AI] Giving up" (Pitfall 2, a confirmed bug-adjacent finding). `SnapshotSessionHost.apply()`'s `persist?.()` also has no catch. The locked decision also requires that "repeated failures escalate loudly: persistence status flips unhealthy" — so this plan adds a `persistenceHealthy` flag that flips false after 3 consecutive failures (mirroring the existing `#aiConsecutiveFailures >= 3` circuit-breaker threshold) and recovers on the next success. Per RESEARCH A1, the dev host wires no persist adapter today — so "both hosts" means the API surface (hook + status + health) must exist symmetrically on both classes.

Output: A never-rethrowing `#persistSafely` wrapper + injectable hook + `lastPersistenceError` status + `persistenceHealthy` flag on GameSession (all 3 sites) and the symmetric shape on SnapshotSessionHost.apply(). The `persistenceHealthy` status is what Plan 126-04's dev-host `record()` uses to escalate a captured persistence entry from 'warning' to 'error'.
</objective>
