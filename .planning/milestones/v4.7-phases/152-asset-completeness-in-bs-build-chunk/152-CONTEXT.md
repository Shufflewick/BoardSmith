# Phase 152: Asset Completeness in bs-build-chunk - Context

**Gathered:** 2026-07-05
**Status:** Ready for planning

<domain>
## Phase Boundary

A game generated by the `bs-build-chunk` pipeline never renders a broken `<img>` for
card/piece art. The fix lives in the skill/scaffold layer (`src/cli/slash-command/bs/build/*.md`,
`src/cli/slash-command/bs/ingest/scaffold.md`, and/or the scaffold UI template + a shared
component), never as a one-off hand-patch to a single generated game. Two guarantees:

1. **ASSET-01** — structural: any card/piece art the build emits routes through a scaffold-shipped
   asset-rendering component that always draws a game-semantic fallback and overlays the real image
   only once it loads, so a missing/unresolved asset degrades cleanly instead of showing a broken
   image.
2. **ASSET-02** — the skill's own automated `test` step gains a build-blocking asset-reachability /
   broken-`<img>` gate, so an asset-referencing-but-asset-less game FAILS the pipeline's bar instead
   of passing green (the exact gap that let DEF-A ship).

Root cause (from v4.6 `149-HUMAN-UAT.md`): `build-chunk` emitted `<img src="/cards/AH.svg">` rules
code without emitting the assets OR guarding the UI to fall back; no automated check caught the
broken `<img>` (tests asserted DOM/handlers only).
</domain>

<decisions>
## Implementation Decisions

### Fallback Strategy (ASSET-01)
- Primary mechanism: a **self-drawn fallback** — the scaffold ships an asset-rendering component
  (e.g. an `<AssetImage>` / card-face wrapper) that ALWAYS draws a token-styled fallback and
  overlays the real `<img>` only once it successfully loads (`onload`), swapping in on failure back
  to the drawn fallback. Broken images become structurally impossible.
- The fallback lives in a **reusable scaffold component**, so every generated game inherits it — not
  per-chunk `build.md` prose alone.
- Fallback is **game-semantic drawn**: cards render rank+suit, pieces render a label, at the asset's
  declared aspect ratio, styled with `DESIGN.md`'s `--bsg-*` tokens (per the existing Placeholder
  Policy) — playable, not merely "not broken."
- Build **never** emits a bare asset `<img>` with no fallback: `build.md` prohibits a raw asset
  `<img>`; all card/piece art routes through the fallback-guaranteeing wrapper.

### Automated Check (ASSET-02)
- The gate is a **new item in `test.md`'s ordered, stop-on-failure sequence** — build-blocking, same
  discipline as the sandbox-lint gate.
- Check is **static asset-reachability**: every asset path referenced by UI source either resolves
  to an emitted file OR is rendered through the fallback wrapper. An unresolved AND unguarded asset
  reference is a failure.
- Severity is **FAIL (hard gate)** — an asset-referencing game shipping no assets and no fallback
  stops the pipeline.
- Scope is **`ui: touches|major` chunks only**, mirroring the a11y-floor conditional (a `ui: none`
  chunk has no UI to check).

### AutoUI Scope (resolved post-research)
- **AutoUI renderers are IN SCOPE.** BoardSmith's own `src/ui/components/auto-ui/renderers/CardRenderer.vue`
  and `PieceRenderer.vue` carry the identical unguarded-`<img>` bug (they branch only on "does
  `$images` exist," never on "did the URL resolve"). A designer using `ui: auto` (the scaffold
  default) hits these, not the custom-UI path — so the phase goal ("a game generated by
  `bs-build-chunk` never renders a broken `<img>`") is only literally true if these are fixed too.
- Apply the same always-drawn-fallback + swap-on-`load` / revert-on-`error` guard to both renderers.
  This is a normal PIT-of-success library fix (2 existing files, already in this repo's test suite),
  NOT a one-off hand-patch to a generated game — it fixes every AutoUI game at once.
- Add a targeted unit test against `CardRenderer.vue`/`PieceRenderer.vue` directly (synthetic
  `load`/`error` events, jsdom-safe per Pitfall 4) — the Go Fish custom-UI regeneration proof does
  NOT exercise the AutoUI path.

### ASSET-02 Wrapper-Detection Heuristic (resolved — Claude's discretion)
- Use the **coarse check** (pit-of-success): the static scanner FAILs on any bare `<img` tag found
  in generated/custom UI source outside the sanctioned `AssetImage.vue` wrapper's own definition —
  no prop-plumbing trace required. Any bare `<img>` is an automatic FAIL regardless of `src`
  content. Trivially cheap, and it makes the wrong path hard rather than exhaustively provable.

### Before/After Proof (Success Criterion 2)
- A **deliberate fixture test in BoardSmith's own suite**: an asset-referencing-but-asset-less
  sample fails the new check; the fallback-wrapped version passes (proves the gate catches DEF-A's
  class).
- **Browser-verify a re-generated Go Fish** (via the `bs-build-chunk` scaffold path) renders every
  card with zero broken `<img>` (`naturalWidth > 0`), with no hand-added asset set.
- Skill-guidance assertions extend **`build-chunk.test.ts` / `templates.test.ts`** to assert the new
  prose (build.md prohibition, test.md gate) and the scaffold component exist.
</decisions>

<specifics>
## Specific Ideas

- The pit-of-success framing is load-bearing: the strongest fix makes a broken `<img>` *structurally
  impossible* (the fallback wrapper is the only sanctioned way to render asset art), with the
  test.md gate as a backstop that fails any code that bypasses the wrapper.
- Regeneration proof target is Go Fish (`~/BoardSmithGames/go-fish`, `/cards/*.svg`), the exact game
  whose DEF-A surfaced in the v4.6 playtest.
</specifics>
