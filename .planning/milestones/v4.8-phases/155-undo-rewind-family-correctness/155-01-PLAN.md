<decisions>
## Locked decisions implemented here

- **D-01 / D-09:** ONE guard in `utils.ts`, called by BOTH executors AND both rewind twins (four
  sites — see Pitfall 3 in RESEARCH.md). Not two parallel patches.
- **D-02 (throw):** the guard **throws** `UndoRefusedError`; it does not return a boolean flag a
  caller can ignore. This is the pit-of-success mechanic: the easy path (call the guard) is the
  correct path, and forgetting the check is the only way to get the old behavior back.
  *Boundary note:* `handleUndo`/`handleDebugRewind` are WS op handlers whose contract is to RETURN
  an `OpResult` — an exception cannot cross the wire. They therefore catch `UndoRefusedError` at
  their own boundary and convert it with `errorResult(err, 'executor', ErrorCode.UNDO_NOT_ALLOWED)`,
  preserving the actionable message verbatim. `undoToTurnStart`'s existing try/catch already does
  the equivalent. The refusal is loud and message-bearing on every path; nothing is a silent no-op.
- **D-04:** `finished`-phase refusal is checked **up front**, before any checkpoint lookup. No
  rolling the phase back via a pre-finish checkpoint.
- **Open Question 2 (RESEARCH.md):** the phase fence and the barrier fence (Plan 02) are two
  independent, composable checks inside the same guard function. Not structurally coupled.
- Error messages name the action and index and MUST NOT contain file paths, line numbers, or stack
  traces (project hard rule).
</decisions>
