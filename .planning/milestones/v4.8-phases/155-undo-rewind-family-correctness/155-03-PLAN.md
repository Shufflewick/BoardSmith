<objective>
Close UNDO-03: delete the game-erasing backward-scan fallback in `computeUndoInfo` and make
`moveCount` authoritative by publishing it on every action step.

Purpose: `getState()` only sets `moveCount` when the action step declares `minMoves`/`maxMoves`
(`engine.ts:579`). Most real games — including Doom Machine, the solo game in the defect report —
declare neither, so `moveCount` is `undefined` and EVERY undo falls into branch C
(`utils.ts:192-213`), which scans backwards for an action by a different player. In a SOLO game
there is no different player, so it walks to index 0 and returns `turnStartActionIndex: 0` — undo
restores the game's initial checkpoint. That is the wipe. This plan removes the fallback entirely.

Output: `moveCount` always published, branch C deleted, missing `moveCount` ⇒ `canUndo: false`, and
the two authoritative undo suites rewritten to the new, deliberately-changed contract.
</objective>

<decisions>
## The semantic change — deliberate, user-approved, NOT a regression to repair

RESEARCH.md §B / Open Question 1 traced line-by-line that `moveCount` is scoped to the active
action-step **frame**, not to a logical player turn that may span several frames. CONTEXT D-06
resolves this explicitly (AMENDED post-research):

> **One undo = one action-step, NOT one turn.**

Consequence: in `collect-turns-fixture`'s two-frame turn, a player who has completed frame #1 and
is now in frame #2 can no longer undo back across the frame boundary. `undo-authoritative.test.ts`
and `stateful-undo-authoritative.test.ts` currently assert `undo.success === true` for exactly that
mid-turn, cross-frame case. **Those expectations are SUPERSEDED. Rewriting them is Task 3's job and
is the intended outcome — it is not test breakage to be repaired back to green by weakening the
fix.**

Explicitly REJECTED (RESEARCH.md §B option 2): turn-scoped `moveCount` accumulation across sibling
frames. Do not build it. It is new engine bookkeeping that does not exist today, and CONTEXT D-06
rules it out.

Also locked: **no back-compat for snapshots lacking `moveCount`** — treat as undo-unavailable
(`canUndo: false`), per the project's no-backward-compatibility hard rule. No replacement fallback
of any kind.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| flow engine → session undo policy | `FlowState.moveCount` is the sole input deciding how far an undo rewinds; a wrong or absent value is directly exploitable as unbounded rollback |
| client → undo op | The client cannot supply `moveCount`, but it can request undo at any moment, including states where `moveCount` is absent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-155-12 | Denial of Service (destructive) | `computeUndoInfo` branch C — a single undo rewinds the entire game to its initial checkpoint, destroying all player progress (D5) | mitigate | Delete branch C entirely; `moveCount` becomes authoritative and always published (Task 2) |
| T-155-13 | Elevation of Privilege | Unbounded rollback lets a player replay an arbitrarily long stretch of the game with knowledge gained from it | mitigate | Same fix bounds every undo to one action-step frame; solo regression test asserts exact incremental rewind (Task 1) |
| T-155-14 | Tampering | Absent `moveCount` silently re-enabling a permissive heuristic | mitigate | Fail-closed: missing `moveCount` ⇒ `actionsThisTurn: 0` ⇒ `canUndo: false`. No fallback exists to reach. |
| T-155-15 | Repudiation | A player whose undo is now refused across a frame boundary gets no explanation | accept | Existing "No actions to undo" message is accurate and actionable for this case; a bespoke frame-boundary message would leak flow-internal structure to the client |
| T-155-SC | Tampering | npm/pip/cargo installs | N/A | No package installs in this phase |
</threat_model>
