<objective>
Deliver VIS-03: a headless DOM-leak test utility that renders the game UI as seat N and fails when
a hidden element's identity (rank/suit/face-image, or any custom attribute) leaks into the rendered
markup.

This is Highest-Risk-Item #2 for v4.4: the matcher itself must have NO blind spots. It derives
forbidden markers by comparing each element's FULL, unfiltered `toJSON()` identity against what
actually SURVIVES into seat N's FINAL per-seat tree (`game.toJSONForPlayer(seat)`, post-playerView,
game.ts:2813-2816). An identity value is forbidden if the element is absent from the final tree, its
node is flagged `__hidden`, or the specific attribute value was stripped/redacted out of the final
node. This closes two blind spots at once: (1) it never trusts the engine redaction allowlist as
ground truth (catches attributes redaction might miss for a game's custom attribute names), and (2)
it honors a game's `static playerView` hook — content the hook hides for seat N (element OR
attribute) becomes a forbidden marker instead of an undetectable leak. A leak-detector with no
failing case is unproven, so the test MUST include a positive control (a deliberately-injected leak
the matcher catches).

Purpose: First DOM-level hidden-info regression guard in the framework.
Output: `src/testing/dom-leak.ts` (new) + jsdom test with positive control + playerView case +
barrel export.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| seat-filtered gameView → rendered DOM | The rendered markup is the actual production leak surface; the matcher guards it |
| matcher configuration (allowlist) → pass/fail verdict | An over-broad allowlist can silently convert a real leak into a false PASS |
| GameClass.playerView post-transform → forbidden-marker set | Content hidden only by the hook must still be a forbidden marker or the matcher has a blind spot |
