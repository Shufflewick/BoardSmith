<objective>
Fix DEF-C: the dev-host multi-client turn-desync. The proven root cause is a stale-close race in the
WebSocket transport layer — `src/cli/commands/dev.ts`'s `socket.on('close', ...)` handler
unconditionally runs `clients.delete(clientId)` + `mpHost.disconnect(clientId)` with no check that the
closing socket is still the one registered for that `clientId`. On a page reload, the NEW socket sends
`hello` with the same persisted `clientId` (DevHost.vue localStorage) BEFORE the OLD socket's `close`
fires; the stale `close` then wrongly flips the reconnected seat's `connected` flag to `false`,
silently dropping all future broadcasts/responses to it → the client's turn view goes stale → the DEF-C
"acted, then rejected / your-turn-when-it-isn't" symptom.

Purpose: Every connected client's turn view stays consistent with the server across reload/reconnect,
proven by a reproduced-then-fixed regression test (DEVHOST-01 root cause, DEVHOST-02 fix + regression).
Output: A one-line socket-identity guard in dev.ts, a real-ws stale-close integration test that fails
pre-fix / passes post-fix, and a fast MultiplayerHost canary — all green, no regression.

This plan is TDD: write the failing real-ws integration test FIRST, watch it fail against the unguarded
close handler, then apply the guard and watch it pass. No changes to MultiplayerHost / SnapshotSessionHost —
they are proven correct (reinitSeat/viewForSeat already deliver a fresh, server-authoritative view).
</objective>

<!-- The bug locus (dev.ts:739-763). Executor uses this directly — no exploration needed. -->
The current (BUGGY) dev.ts connection handler, in `wss.on('connection', (socket) => { ... })`:
- On `message` with `type === 'hello'`: sets `clientId` from `msg.clientId`, `clients.set(clientId, socket)`, then `dispatch(clientId, { type: 'hello' })`.
- On `close` (UNGUARDED, the bug): `if (clientId) { clients.delete(clientId); mpHost.disconnect(clientId); }`.
The `clients` map is `Map<string, WebSocket>`; the `send` adapter does `clients.get(clientId)` and only sends if the socket is OPEN. `mpHost.disconnect(clientId)` sets the seat's `connected=false`, which `deliverGameState`/`deliverServerResponse` in multiplayer-host.ts consult before delivering.

<!-- The fix (the ENTIRE change to dev.ts): -->
Guard the close handler so it only tears down when the closing socket still owns the mapping:
only run `clients.delete(clientId)` + `mpHost.disconnect(clientId)` when `clientId && clients.get(clientId) === socket`. A page reload opens a new socket (same persisted clientId) whose `hello` can be processed before the older socket's `close` — Node gives no ordering guarantee; if a newer connection already claimed the mapping, the close is stale and must be ignored.

<!-- Existing test harness shapes to REUSE (do NOT build new infra): -->
- multiplayer-host.test.ts: `makeAltHost()` returns `{ host, to, pass, clear, ... }`. `to(clientId)` = messages sent to that client; `pass(clientId, requestId)` submits a `pass` action; `clear()` empties the sent buffer. Existing reconnect test at "re-inits a seat on reconnect (same clientId) mid-game" (line ~148) drives `hello → disconnect → hello` (the EXPECTED order). The bug is the REVERSED order — `hello (reconnect) → disconnect (stale)`.
- dev-host.integration.test.ts: stands up a REAL `WebSocketServer({ port: 0 })` wired to MultiplayerHost, mirroring dev.ts (comment: "Mirrors dev.ts:559-583"). Its own `wss.on('connection', ...)` assigns a NEW `client-${++clientCounter}` per connection (line ~102) — so two connections never collide on one clientId there today (Pitfall 2). The new test needs its own connection handler whose clientId comes from the `hello` message (dev.ts-faithful), so two sockets can share ONE clientId.
