<objective>
Close the durable-barrier half of UNDO-02: an undo must not rewind through a completed `execute()`
node.

Purpose: `frame.completed` (`engine.ts:1557`) is transient — it does not survive checkpoint restore
— so it cannot be the fence. Games use `execute()` for irreversible side effects (scoring, dealing,
revealing hidden info); rewinding through one is the data-loss / hidden-info-rewrite defect D2
reports.

Output: a monotonic `executeBarrierIndex` on `GameRunner`, persisted as a `GameStateSnapshot`
sibling of `actionCheckpoints`, and a third composable check inside the Plan 01 shared guard.
</objective>

<decisions>
## Design decision (CONTEXT grants discretion on shape; RESEARCH.md §A recommends this)

**Chosen: a single monotonic `executeBarrierIndex: number` on `GameRunner`, persisted as a
top-level `GameStateSnapshot` field beside `actionCheckpoints`.** Rejected alternatives, per
RESEARCH.md §A:
- *Per-history-entry boolean* — more storage, no benefit; the check is inherently a single
  high-water mark.
- *Flow `frame.data`* — explicitly rejected. Frame data is keyed to flow structure; the fence is
  keyed to an action INDEX. Correlating the two needs a second index and is the wrong shape.

The check is O(1): `turnStartActionIndex < executeBarrierIndex` ⇒ refuse.

**Signalling mechanism:** `FlowEngine` gets a public monotonic `executeNodeCompletions` counter
incremented in `executeExecute`. `GameRunner` records its last-seen value; after each action append,
if the counter advanced, it sets `executeBarrierIndex = this.actionHistory.length`. Because restore
builds a fresh FlowEngine (counter back to 0), the runner **re-baselines** its last-seen value to
the live counter immediately after `fromSnapshot`/`fromCheckpoint` restore, and adopts
`executeBarrierIndex` from the snapshot — the persisted number, not the counter, is the durable
fact. This is what makes the fence survive checkpoint restore, which is the entire point of D-03.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → undo/rewind op handlers | An attacker-controlled `actionIndex` on `debugRewind` selects an arbitrary point in history |
| persisted snapshot → restored runner | Snapshot content is trusted state, but a MISSING barrier field must not silently disable the fence unnoticed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-155-05 | Tampering | Rewinding through a completed `execute()` node rolls back committed, irreversible game state (D2 data loss) | mitigate | Durable `executeBarrierIndex` + guard check at all four entry points (Tasks 2-3) |
| T-155-06 | Information Disclosure | Rewinding past an `execute()` that revealed hidden information lets a player re-decide with knowledge they should not have (hidden-info rewrite) | mitigate | Same fence; the barrier is set the moment the execute node completes, before the next action is recorded |
| T-155-07 | Tampering | Fence defeated by forcing a snapshot round-trip (transient `frame.completed` is lost on restore) | mitigate | Barrier persisted in `GameStateSnapshot` and re-adopted in `fromSnapshot`/`fromCheckpoint`; Task 1 includes an explicit durability-across-round-trip case |
| T-155-08 | Elevation of Privilege | `debugRewind` with an arbitrary client-supplied index bypasses the undo fence | mitigate | `handleDebugRewind` and `rewindToAction` call the same guard with the target index (Plan 01 Task 2 + this plan Task 3) |
| T-155-SC | Tampering | npm/pip/cargo installs | N/A | No package installs in this phase |
</threat_model>
