<objective>
Close DEVHOST-02 (D14, solo start) and DEVHOST-04 (D16, canonical palette source) — the two
dev.ts "honor what the game definition declares" defects that are file-disjoint from the
multiplayer-host work in Plans 02-04.

Purpose: (D14) `cli.ts:36` hardcodes `--players` default `'2'`, and `resolveEffectivePlayerCount`
(dev.ts:85) ERRORS when the count is out of `[minPlayers,maxPlayers]`. A solo game
(maxPlayers=1) therefore hard-errors on a bare `boardsmith dev` (default 2 > max 1). The game already
tolerates `playerCount:1`; the defect is purely the CLI default. (D16) dev reads the color palette
ONLY from `boardsmith.json` (dev.ts:545), so a game that declares its palette in code drops to the
engine red/blue/green (`game.ts:659` `options.colors ?? DEFAULT_COLOR_PALETTE`).

Output: `--players` defaults to the game's `minPlayers` (explicit range-check retained); a new
`GameDefinition.colorPalette` field (session/types.ts) plus an ordered dev palette resolver
(gameDefinition → boardsmith.json → engine default) threaded through the existing
`colorPalette`/`buildDevConfig`/`MultiplayerHost` path, with net-new regression coverage.
</objective>

<decisions>
## Locked decisions implemented here (CONTEXT.md D14, D16)

- **D14:** default `--players` to `gameDefinition.minPlayers`, NOT the literal `'2'`. Because the flag
  is parsed before the game loads, remove the `cli.ts` default so `options.players` is `undefined`
  when unset, and resolve the default AFTER `minPlayers` is known. `resolveEffectivePlayerCount`
  still range-checks an EXPLICIT `--players` and errors on out-of-range (unchanged).
- **D16:** add `GameDefinition.colorPalette?: Array<{ id: string; hex: string; label: string }>` —
  the validated shape, not a new one. Dev fallback order is EXACTLY
  `gameDefinition.colorPalette → boardsmith.json config.colorPalette → engine DEFAULT_COLOR_PALETTE`.
  This ordered default chain is a legitimate precedence rule, NOT a dummy-data fallback.
- **D16 additive/minimal (Low severity):** reuse `normalizeColorPalette` and the existing
  `colorPalette` threading through `buildDevConfig`/`MultiplayerHost`. Do NOT touch the per-seat
  color plumbing in `multiplayer-host.ts` — it already consumes the resolved palette.
- **Deferred (CONTEXT deferred idea #3):** publish-side unification (making `publish` read
  `GameDefinition.colorPalette`) is OUT OF SCOPE. This plan adds the GameDefinition source for DEV
  only; `publish` already writes `manifest.colorPalette` from its own source.
- Error messages stay actionable and leak no paths/line numbers/stack traces (project hard rule).
</decisions>
