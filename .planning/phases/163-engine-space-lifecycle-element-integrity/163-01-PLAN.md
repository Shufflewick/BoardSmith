<objective>
Close SPACE-01 (sealed / append-only Space, D22) and SPACE-02 (Space removal / re-parent, D23)
together, because both live in the SAME element-movement machinery (`moveToInternal`, the exit/enter
events, and the cycle guards). Today only `Piece` has `moveToInternal`/`putInto` (`piece.ts:74,81,186`);
`Space` cannot be relocated at all, and no `Space` can refuse child removal.

Purpose: a sealed Space (D22) is a append-only zone (e.g. a permanent tableau row) whose `onExit`
side-effects must never be silently undone by a stray removal, and must not corrupt the tree if a
removal is rejected. Space re-parent (D23) lets a game tear down / relocate a slot instead of the
current slot-outlives-part model. Both require one honest refactor: lift `moveToInternal` from `Piece`
to `GameElement` so Pieces AND Spaces share ONE splice+exit+enter+cycle-guard path, and put the
sealed-old-parent check in that one path so it cannot be bypassed by a new caller.

Output: `moveToInternal` on `GameElement`, a `sealed` flag + a re-parent/remove method on `Space`, and
net-new `space.test.ts` coverage including a sealed-survives-restore round-trip.
</objective>

<decisions>
## Locked decisions implemented here (D22, D23)

- **D22 seal is about CHILD REMOVAL only** — reject a Piece being spliced OUT of a sealed Space.
  ADDING is allowed (append-only). The check throws BEFORE the splice so a rejected removal leaves
  `_t.children` / `_t.parent` untouched (no corrupt-on-reject — RESEARCH Pitfall).
- **D22 restore bypasses by design** — restore is not a logical exit; onExit effects are already in the
  serialized state and handlers are re-attached. Restore rebuilds via `addChild`, never `moveToInternal`,
  so the seal check is bypassed for free. A test MUST assert sealed-flag + onExit-effect survive restore.
- **D23 re-parenting fires the Space's OWN onExit** on the parent it leaves (a logical exit); its
  children go with it and fire NO child exit events (their parent — the moved Space — is unchanged).
- **D23: a sealed Space can still be re-parented** — the seal fences child removal (D22), not the
  Space's own relocation. Keep the two concerns independent.
- **One path, not two patches:** lift `moveToInternal` to `GameElement` (Claude's-discretion approach
  per CONTEXT) so Piece and Space share the splice/exit/enter/cycle machinery and the sealed check has
  exactly one home it cannot be routed around. No backward-compat shim on `Piece.putInto` — it keeps
  its signature and delegates to the inherited method.
- Error messages name the Space and say what to do; NO file paths, line numbers, or stack traces.
</decisions>
