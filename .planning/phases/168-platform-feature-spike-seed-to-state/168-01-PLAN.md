- `## Problem` — restate C.1 from BATTERY-POST-MORTEM.md (bigger games take a long time to play up to the feature under test; seed the game into the exact target state so the human arrives not-already-annoyed). Note this is high-leverage on human-in-the-loop quality.
- `## Mechanism` — the seed IS a serialized GameStateSnapshot JSON (the existing format), NOT a new format. Enumerate the fields that carry the state (`state`/`game.toJSON()`, `flowState`, `sequence`, `randomState`, `gameOptions`) and state that determinism is already covered by the snapshot's `seed` + `randomState` (a single mulberry32 RNG state number) — both already restored on load. Call out that `actionHistory` is needed only for undo, not to REACH the state, so a seed needs no real play history.
- `## Load path` — describe the state-authoritative deterministic restore via GameRunner.fromSnapshot (rebuilds tree via loadSerializedState, restores RNG via setRandomState, rebuilds flow via restoreFlowState — NOT a replay). Name both entry points: the stateless dev-host path (executeOp → handleStart in stateless-ops.ts) and the stateful GameSession.restore path. State that the load machinery already exists and is exported (src/runtime/index.ts, src/engine/index.ts).
- `## Authoring surface` — record-from-play is the primary path: drive a TestGame with real actions to the target state, then capture TestGame.getSnapshot() and write it to a seed file. Zero new engine work. Note hand-authoring / snapshot-validation (author a board position without playing to it) as a DEFERRED future enhancement (surface-don't-overreach).
- `## Pipeline request API` — the pipeline requests a target state via a NAMED SEED FILE the playtest step loads. Document a concrete file-location convention (Claude's discretion — e.g. a `seeds/<scenario>.json` convention under the game project) and how a future bs-skills playtest script would reference a named seed. State clearly that NO skills edits are made in this phase — the API shape is documented for a future wire-up only.
- `## Dev-host wiring` — describe the `--seed <file>` flag added to `boardsmith dev` (built by plan 168-02): at game start it seeds the host's initial snapshot from the seed file INSTEAD OF handleStart's freshly-started snapshot; because the host treats the snapshot as opaque authoritative state, this is a small change and reuses the existing fromSnapshot path (no new load machinery).
- `## Cost / shape recommendation` — the feasibility finding: loading is solved and exported; the ONLY genuinely new work is (a) the record-from-play authoring convenience and (b) the small `--seed` wiring flag. Recommend shipping the raw-snapshot seed (no higher-level scenario DSL) until raw authoring proves too low-level in practice. Give a rough relative-cost read (low), grounded in "load path already exists."
- `## Proven vs deferred` — state exactly what the Phase 168 PoC proves (deterministic record→seed→load→assert against a target state, via the `--seed` path; load-twice-identical) and what is deferred (hand-authoring helper; bs-skills playtest wire-up; scenario DSL — all listed in 168-CONTEXT.md Deferred Ideas). State explicitly that feature C.2 (panel multi-select) is delivered by Phase 159 (AI-01), NOT by this phase.

Cite the real building-block files by path (and approximate symbol/line) from <read_first> wherever a claim rests on existing code — GameStateSnapshot (snapshot.ts), GameRunner.fromSnapshot / getSnapshot (runner.ts), handleStart / executeOp (stateless-ops.ts), GameSession.restore (game-session.ts), TestGame.getSnapshot (test-game.ts). Every citation must name a file that exists. Do not invent APIs; if unsure of a symbol, re-read the file rather than guess.
