  <action>
    Use the `one-two-punch` copy (a second, independent game — plan 173-06 used `seven`, so this
    also gives the pipeline a second real-data exercise). If its rulebook has too few slice-units to
    produce a meaningful partial state (fewer than three), use a fresh `seven` copy instead and say
    so in the proof.

    Follow RESEARCH.md's concrete proposal:
    1. Start a real verify pass, following the installed skill as in plan 173-06.
    2. Let it run until `verify-run-status --json` shows AT LEAST ONE unit recorded and AT LEAST ONE
       still unrecorded. Capture that intermediate `--json` output verbatim — this is the "before"
       state the whole proof rests on.
    3. Deliberately interrupt: terminate the dispatching process mid-pass. If the dispatch is driven
       by a script, `kill -9` it mid-loop; if it is the live session itself, abort the pass after
       confirming the mixed recorded/unrecorded state. State which of the two happened.
    4. Re-invoke the pass against the SAME project, letting the skill find and resume the open run
       exactly as its resume step instructs — do not pass hand-computed state in.
    5. Assert, each independently:
       (a) the already-recorded unit(s) are NOT re-dispatched — no second dispatch prompt for that
           unit appears in the resumed transcript, no second RUN.md record for it exists, and the
           already-staged slice file's mtime and sha256 are unchanged across the resume;
       (b) the unrecorded unit(s) ARE dispatched — their prompts appear and their records get
           appended;
       (c) the final state matches a clean, uninterrupted run: same set of unit ids recorded, same
           set of staged slice files, and a `verify-run-status --json` `count` equal to the unit
           count. Compare against plan 173-06's clean run for the same game where applicable, or run
           a clean pass on a second copy to compare against.
    6. Also record whether the session used `verify-run-status` to decide what to resume, or fell
       back to eyeballing which files exist. The latter is a Phase-170-class finding even if the end
       state is correct — report it.

    Then exercise the crash-safety edge the ledger design claims: truncate the last in-fence line of
    a RUN.md copy mid-JSON, run `verify-run-status --json`, and confirm the affected unit is
    reported as NOT recorded (so resume re-dispatches it) rather than as complete. Record the
    verbatim output.

    Capture the resumed session's transcript to `$SCRATCH/173-resume-transcript.log` and re-run the
    SC-3 absence grep against it too — the resumed orchestrator must also never read a slice.

    Write the assertions into a re-runnable `$SCRATCH/173-sc4.sh`, then append a
    `## 4. SC-4 — kill and resume` section to `173-PROOF.md` with all output verbatim.

    Post-run: re-verify BOTH originals byte-identical.
  </action>
