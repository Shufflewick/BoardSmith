# Plan 173-08 — Ledger crash-safety + resume determinism

## Objective

Close the two load-bearing defects the Phase 173 evidence chain surfaced *after* its plans were
written: the ledger's write is not crash-safe (code review CR-01, **Critical**), and range-level
resume is not idempotent (`173-PROOF.md` §4 Finding 1, **user-directed fix**). Plus the review's
WR-01 and three Info items.

Both defects are in the same subsystem and both undercut VERIFY-08, which 173-07 marked complete.
Fixing them together, before Phase 174 builds on the guarantee.

## Why now, not in 174

Phase 174's classifier compares staged slices against live ones. Finding 1 means a **resumed** pass
stages differently-bounded, overlapping content versus a clean pass — measured at 9 recorded units
vs 4 on `one-two-punch`. That changes the comparison surface itself, which is a false-positive
generator, and VERIFY-03's entire purpose is that independent re-wording must not flag every chunk.
The user chose "fix now, before 174" when presented with the alternatives.

CR-01 is worse and was not a user choice: it is a Critical that makes the crash-safety guarantee
VERIFY-08 rests on false.

<task type="auto" tdd="true">
  <name>Task 1: Make the ledger write crash-safe (CR-01, Critical)</name>
  <files>src/cli/commands/verify-run.ts, src/cli/commands/verify-run.test.ts</files>
  <behavior>
    - A crash at ANY point during a record append leaves the ledger either exactly as it was before
      the call, or with the new record fully written. Never truncated, never partially rewritten,
      never missing previously-durable records.
    - Records written by earlier, already-completed calls survive a crash during a later call.
    - The existing torn-final-line read semantics are UNCHANGED: an unparseable trailing line still
      reads as NOT recorded, so resume re-dispatches that unit (this is 173-07's proven behavior —
      do not regress it).
  </behavior>
  <action>
`verify-run.ts:389` is `await fs.writeFile(ledgerFile, newText)` — no flag, so Node uses `'w'`
(`O_TRUNC`). Every append is a full read-modify-**rewrite**: the file is truncated to zero and
rewritten from scratch. A crash inside that window destroys the WHOLE ledger, including records from
earlier completed calls — not merely the final line.

This directly contradicts the module's own doc comment at `verify-run.ts:25` ("a torn append can
damage at most the final line"), which is the guarantee 173-07's SC-4 proof and VERIFY-08 rest on.

Replace with an **atomic write**: serialize to a temp file in the same directory, `fsync` it, then
`rename()` over the target. POSIX `rename()` within a filesystem is atomic — a crash leaves either
the complete old file or the complete new one, never a torn one. Same-directory is required for the
rename to stay within one filesystem.

Do NOT switch to `fs.appendFile`: the ledger is a FENCED region and a new record must land BEFORE the
closing fence, so a raw append would write outside it and corrupt the structure. The fence is why the
whole-file rewrite exists; atomicity is the fix, not append.

Then correct the doc comment at line 25 to state what is actually guaranteed. While there, close
**Finding 2** from `173-PROOF.md` §4 — the stated wording does not cover a crash that also destroys
the trailing fence (that case throws). With an atomic write that shape becomes unreachable, so say
so precisely rather than leaving prose that overpromises.
  </action>
  <verification>
    - A test that simulates the crash window (e.g. inject a failure between temp-write and rename)
      and asserts the ledger is byte-identical to its pre-call state, with all earlier records intact.
    - Existing torn-line tests still green — the read-time demotion behavior must not change.
    - `grep -n "fs.writeFile(ledgerFile" src/cli/commands/verify-run.ts` returns nothing.
  </verification>
  <automated>npx vitest run src/cli/commands/verify-run.test.ts</automated>
</task>

<threat_model>
- **T-173-08-01 — ledger destruction on crash (the CR-01 defect itself).** Mitigated by the atomic
  temp-write + `rename()` in Task 1. Same-directory temp file keeps the rename within one filesystem.
- **T-173-08-02 — temp-file collision between concurrent runs.** Temp name must be unique per call
  (run-id + unit + pid or a counter); never a fixed `.tmp` suffix that two passes could share.
- **T-173-08-03 — traversal via the persisted manifest.** The dispatch-plan manifest's paths are
  written by the command and read back into filesystem operations. Re-validate on read with the same
  fixed-shape regex + resolve-and-prefix assertion `run-id` already uses. A persisted file is
  untrusted input on the next run.
- **T-173-08-04 — stale temp files leaking into the staging tree.** A crash between temp-write and
  rename leaves a temp file. It must not be mistaken for a staged slice or a ledger by any reader.
</threat_model>
