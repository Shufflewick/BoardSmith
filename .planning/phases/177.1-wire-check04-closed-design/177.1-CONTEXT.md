<decisions>
## Implementation Decisions

### Area 1 — CLI surface and the ledger (accepted 2026-07-31)

1. **Command names: `verify-derive-check` (read/report) + `verify-derive-record` (sole write
   surface).** "Recheck" and "re-derivation" named the RETIRED mechanism; "check" is
   design-neutral and survives a future design change. Keeping `verify-derive-record` preserves
   the single-write-surface identity CR-05 established. The `--verdict` enum changes to the
   dual-enumeration set — this is a deliberate, documented semantic change, not a silent one.

2. **MOVE the existing ledger machinery wholesale; never rewrite it.** Atomic upsert-append
   (CR-06), fence-injection rejection (CR-04), read-path revalidation through the single choke
   point (CR-02), evidence requirement (WR-05). That code survived an 18-finding review in
   177-09/177-10. Only the verdict enum and the record's judgment fields change.

3. **The SKILL orchestrator dispatches the enumerator and reconciler subagents; the CLI builds
   payloads, validates grounding, composes arithmetic, classifies, and records.** Identical to
   Steps 5 and 6, and it is what keeps `verify-game.md`'s "formatted, never computed" discipline
   true. The CLI must NOT shell out to `claude -p` itself — that was the `.planning/` harness's
   shape, appropriate for a measurement driver and wrong for the product.

4. **Pin the explicit cross-family model ids in the contract**: `claude-opus-5` and
   `claude-haiku-4-5-20251001` as the two independent enumerators, `claude-sonnet-5` as the
   reconciler. Cross-family independence was load-bearing in every measurement (`177-22` used
   exactly these). Leaving model choice to an orchestrator default would silently change what was
   measured and quietly weaken the independence premise the whole design rests on.

### Area 2 — Removal scope (accepted 2026-07-31)

5. **DELETE the targeting-specific machinery** — `buildBlindDerivePayload`, `focusQuoteWindow`,
   `blindDeriveHandle`, `factAlignment`, the four-verdict enum
   (`agrees`/`disagrees`/`underivable`/`not-rule-bearing`), `verify/derive-recheck.md`,
   `verify/derive-compare.md`, and the `verify-derive-recheck` command. Removed, not deprecated,
   per the project's No Backward Compatibility rule.

6. **MOVE the design-agnostic parts** the CHECK-04 closure note already named as carrying forward
   unchanged: the ledger, the write surface, enumeration, and the blind-independence guarantee
   (CR-01's decoration-proof strip, CR-07's opaque handle discipline). Anything genuinely still
   needed by the new path is moved into it — never left behind as a second live path.

7. **Rewrite `verify-game.md`'s Context-Economics carve-out for the new dispatches** (lines
   49-64). It currently names `derive-recheck.md`, `derive-compare.md`, `BS-DERIVE-V1`,
   `BS-DERIVE-COMPARE-V1`, and `buildBlindDerivePayload` explicitly. **Preserve its two-observable
   reviewer check** — that structure is the valuable part — re-aimed: the enumerator payload
   (`BS-ENUMERATE-V1`) legitimately carries quote lines and must contain ZERO annotation lines,
   while the reconciler (`BS-RECONCILE-V1`) prompt/return legitimately carries fact statements.
   Also update Reference Files (lines 226-231).

8. **Consolidate the duplicated annotation-family regexes to ONE exported definition.** Five
   sites (measured reality #6). We are already editing two of them, and Phase 178 adds a 4th
   line-kind (`Example (p.N):`) — leaving five copies means Phase 178 must widen all five in
   lockstep or silently break one. This is the cheap, safe half of the cleanup.

9. **WR-07 (`quoteLinesOnly` deny-list → allow-list inversion) stays OPEN — close it in Phase
   178.** Inverting the list changes behavior and deserves its own evidence, and Phase 178 is
   where the 4th kind actually lands. Consolidating (decision 8) is safe; inverting is not. Do
   not silently drop it: it remains recorded as open, dated 2026-07-30.

### Area 3 — Proving the product path (accepted 2026-07-31)

10. **The comparison target is a specific slice already recorded in `177-22-MEASUREMENT/`**, whose
    per-line results and raw dispatch data are committed. Re-run that exact input through the new
    CLI + skill path and compare against the recorded result.

11. **The bar is SPLIT, and each half is checked for satisfiability BEFORE it is committed:**
    - **Mechanical outputs must agree EXACTLY** — payload bytes, candidate-line selection,
      grounding validation results, arithmetic composition. These are deterministic functions of
      the input; an exact bar here is both strict and reachable.
    - **Model-dependent classification must land WITHIN the label set `177-20`/`177-21`/`177-22`
      observed for that line.** Demanding exact label agreement would re-import the retired
      determinism gate against a known ~12.5% cross-run variance — unsatisfiable by construction,
      the exact trap that cost Phase 177 four full measurement runs.

    This split is the phase's most important decision. A criterion no correct implementation could
    satisfy is a defect in the criterion.

12. **Pre-register both halves before dispatching.** Cheap here because the mechanical half is
    fully predictable from a ZERO-DISPATCH DRY RUN — the technique that predicted
    `targetingAmbiguousCount` exactly (4/16) in 177-11. Commit the expected mechanical outputs and
    the permitted label set first, then run.

13. **`cp -R` staging, sha256 baselines, originals proven byte-identical after** — the discipline
    held across 200+ live dispatches in both Phase 177 proof runs.

14. **Advisory, exit 0, never gates the Close.** CHECK-04 decision 15 must survive the rewiring
    unchanged — a rewiring is exactly the kind of change that silently alters a gate.
