### CR-01/CR-02/CR-03: free-text-keyed lookups in the dual-enumeration compute pipeline fail closed on collision, never silently substitute an operand or evidence fact

**Files modified:** `src/cli/commands/verify-enumerate.ts`, `src/cli/commands/verify-derive-check.ts`, `src/cli/commands/verify-enumerate.test.ts`, `src/cli/commands/verify-derive-check.test.ts`
**Commit:** `d6e14de8`
**Applied fix:** Fixed as ONE shared-pattern change, per the review's own instruction ("Fix that
pattern once — id-based keys, fail-closed on collision — rather than patching three call sites
independently"):

- **CR-01** (`resolveArithmeticSpec`): `groundedByStatement` (now built by
  `buildGroundedByStatement`) maps a colliding `statement` to an `AMBIGUOUS_OPERAND_STATEMENT`
  sentinel instead of overwriting with the last-inserted fact. Every lookup site (`single` and
  `chain` operand resolution, and `citedFactIds`) checks for the sentinel explicitly and reports an
  unresolvable operand — same posture as "not found," never a usable operand.
- **CR-02** (`reconcileSlice`): `composedFactId` is now carried through a
  `composedFactIdByIndex: Map<number, string>` keyed by each proposal's own index in
  `derivedLineProposals`, populated in the same loop that attempts composition — never re-derived
  afterward via `composed.find(c => c.claimText === prop.derivedLineText)`. Two Derived lines with
  byte-identical text no longer risk one inheriting the other's composed-fact citation.
- **CR-03** (`findMatch`/`validateGrounding`): when several facts tie at the winning match rank
  (the documented normal case — several facts sharing one `sourceSentence`), the tie is now broken
  by `tokenOverlapScore` — normalized-word-set overlap between the claim's own `statement` field and
  each tied candidate's `statement` — rather than a deterministic-but-arbitrary content-id order.
  When zero or more than one candidate wins that score, `findMatch` returns `{ kind: 'ambiguous' }`
  and `validateGrounding` reports an explicit `GroundingRejection` naming the collision, never a
  silent pick.

An earlier, simpler CR-03 attempt (disambiguating via `isTolerantMatch`/containment against the
claim's own statement) was tried first and **failed** the pinned reference-measurement test
(`reconcileSlice` reproducing `analysis-run1.json`'s `groundedBothCount 9` dropped to 4) — containment
is too strict for independently-authored prose that describes the same fact in different words with
no substring relationship at all. The token-overlap scoring approach was substituted and reproduces
the reference exactly (`groundedBothCount 9`, composed id `ccb54c72d6b176e1`, value 112) while now
being collision-safe — this iteration is recorded in `177.1-08-SUMMARY.md`'s new addendum.

**Tests that prove the fix (fail before / pass after):**
- `verify-derive-check.test.ts`: *"CR-01: two grounded 'both' facts sharing identical statement
  text fail closed..."* — two "both" claims deliberately share `statement` text ("Shared label.")
  but ground to different magnitude-4/magnitude-9 facts; asserts the arithmeticSpec now refuses
  (`ambiguousIndex` reason) rather than silently composing against whichever fact won last-write.
- `verify-derive-check.test.ts`: *"CR-02: two Derived lines sharing identical text — the SECOND
  proposal (rejected arithmetic) never inherits the FIRST proposal's composedFactId"* — line 5's
  correct spec composes; line 12's byte-identical text but wrong `claimedResult` now falls through
  to `uncorroborated` instead of citing line 5's composed fact.
- `verify-enumerate.test.ts`: *"CR-03: two 'both' claims quoting the SAME sourceSentence ground to
  DIFFERENT facts when each claim's own statement disambiguates"* — draw/discard collision case
  modeled directly on the review's own example.
- `verify-enumerate.test.ts`: *"CR-03: when the claim's own statement does NOT disambiguate... the
  claim is REJECTED"* — proves the fail-closed path, not just the happy path.
- Existing `reconcileSlice` fixture test reproducing `analysis-run1.json` exactly (groundedBothCount
  9/19, composed ids `ccb54c72d6b176e1`/`580cab72645565db`) — unchanged, still green, proving the
  fix does not regress the measured reference this phase's closure evidence rests on.

D-14 preserved: every collision downgrades the affected line/claim to an honest
`uncorroborated`/rejected verdict with a named reason string — none of these paths set
`process.exitCode` or throw for a data condition.

### CR-04: `--slice-path` path traversal on `verify-derive-record`

**Files modified:** `src/cli/commands/verify-derive-check.ts`, `src/cli/commands/verify-derive-check.test.ts`
**Commit:** `22cd9492`
**Applied fix:** Added a containment guard mirroring `verify-classify.ts`'s `--live-slice` guard
(T-174-14) exactly, adapted for `--slice-path`'s existing `rulebook/<file>` shape (unlike
`--live-slice`, which is bare-relative-to-`rulebook/`): resolves `slicePath` against `projectDir`,
requires the result stay inside `projectDir/rulebook` via `relative()` + `startsWith('..')` +
`isAbsolute()` checks, validated BEFORE `fs.readFile` is ever called.

**Test that proves the fix:** `verify-derive-check.test.ts`: *"CR-04: --slice-path escaping
rulebook/ (path traversal) is rejected BEFORE any read, never reads an arbitrary local file"* —
writes a `secret.txt` outside `rulebook/` at the project root, asserts `verify-derive-record`
rejects `rulebook/../secret.txt` with a `resolves outside` error and the secret's contents never
appear in the thrown message; a second case proves a deep `../../../../../../etc/passwd` traversal
is rejected the same way.
