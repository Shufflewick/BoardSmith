# Phase 177.1: Code Review Report

**Reviewed:** 2026-07-31T00:00:00Z
**Depth:** deep
**Files Reviewed:** 9
**Status:** issues_found

## Summary

The moved ledger machinery (`createDeriveCheckRecord`, `recordDeriveCheckVerdicts`/
`replaceDeriveCheckVerdicts`, `readDeriveCheckVerdicts`) genuinely preserves CR-06 (upsert-append),
CR-04 (fence rejection at construction), CR-02 (read-path re-entry through the same choke point),
and the WR-05 evidence requirement — these guarantees were checked against the actual
implementation, not just test presence, and all four hold.

The import cycle (`verify-enumerate.ts` ↔ `verify-derive-check.ts`) is genuinely safe under native
ESM today: neither module evaluates the cross-imported binding at top-level module-init time, only
inside function bodies invoked after both modules finish loading. That said, nothing enforces this
invariant going forward (see WR-02 below).

The real problems are in `reconcileSlice`'s operand/evidence resolution: three separate places key
a lookup by free-text (model-supplied) strings — `statement`, `sourceSentence`, `derivedLineText` —
rather than by a stable identifier, and each collapses distinct facts/proposals that happen to share
identical text. This is exactly the class of gap the "what matters most" brief asked to be proven
out, and it is real, not hypothetical: a reconciler proposal with a wrong `claimedResult` can be
made to pass by exploiting any of the three collisions below. There is also a path-containment gap
on `--slice-path` that the sibling `verify-classify.ts` command already guards against and this one
does not.

## Critical Issues

### CR-01: `resolveArithmeticSpec`'s `groundedByStatement` map silently collapses distinct grounded facts that share identical `statement` text

**File:** `src/cli/commands/verify-derive-check.ts:1067` (map construction), `:963-1030` (`resolveArithmeticSpec`)

**Issue:** `groundedByStatement = new Map(grounding.grounded.map((g) => [g.statement, g]))` is keyed
by the reconciler's own free-text `statement` field. Nothing enforces `statement` uniqueness across
a slice's "both" claims — it is model-authored prose describing each corroborated fact. If two
distinct `ReconcilerBothClaim`s (grounding to two different, correctly-validated
`GroundedBothFact`s with different `matchedFactA`/`matchedFactB`, i.e. different `numericValue`s)
happen to carry the same `statement` string, the later entry silently overwrites the earlier one in
the `Map`. Any `arithmeticSpec.operandStatements`/`operandRefs` pointer that names that shared
statement text always resolves to the *last*-inserted fact, never the one the reconciler actually
intended for that operand slot.

Because arithmetic composition is the mechanism this module exists to keep honest ("code performs
the arithmetic and must reject a wrong `claimedResult`"), a reconciler (hostile or merely
confused/model-drifted) can exploit this: submit two "both" claims with identical `statement` text
but different `quotedFromA`/`quotedFromB` (grounding to two real, different facts with different
magnitudes), then point an `arithmeticSpec` at that shared statement text while writing a
`claimedResult` computed from the second (silently-winning) fact's magnitude instead of the first.
`composeArithmeticClaim`/`composeArithmeticChain` will faithfully validate arithmetic against
whichever fact won the map collision — which is not necessarily the fact the citation was
supposed to name — so a `claimedResult` that has no genuine support from the *intended* operand can
still validate.

**Fix:** Key the map by the grounded fact's own `id` (already unique, sha256-derived), and have the
reconciler / `ArithmeticSpecSingle.operandStatements` (or an added `arithmeticSpec.operandIds`)
resolve through `id`, not `statement`. At minimum, detect the collision and refuse
(`resolveArithmeticSpec` should error/fail-closed with "ambiguous operand statement" rather than
silently picking the last write) if two grounded facts in the same slice ever share a `statement`.

```ts
const groundedByStatement = new Map<string, GroundedBothFact>();
for (const g of grounding.grounded) {
  if (groundedByStatement.has(g.statement)) {
    // fail closed instead of last-write-wins
    groundedByStatement.set(g.statement, AMBIGUOUS_SENTINEL);
    continue;
  }
  groundedByStatement.set(g.statement, g);
}
```

### CR-02: `reconcileSlice`'s `composedFactId` lookup collapses distinct proposals that share identical `derivedLineText`

**File:** `src/cli/commands/verify-derive-check.ts:1095-1112`

**Issue:**

```ts
let composedFactId: string | undefined;
if (prop.proposedClassification === 'corroborated-by-composition') {
  composedFactId = composed.find((c) => c.claimText === prop.derivedLineText)?.id;
}
```

`composed` is a flat pool accumulated across *every* `corroborated-by-composition` proposal in the
slice (built in the earlier loop at lines 1072-1093). The lookup here matches by `claimText`
(`= derivedLineText`) alone — never by `lineNumber` or proposal identity. If two different
`Derived (p.N):` lines in the same slice happen to have byte-identical text (a repeated legend line,
a duplicated annotation, or two occurrences of the same templated sentence — all plausible in real
rulebooks, and trivially constructible by an adversarial/confused reconciler), then:

1. Proposal A (line 5) supplies a *correct* `arithmeticSpec` → `resolveArithmeticSpec` succeeds →
   pushed into `composed` with `claimText === "Derived (p.3): 7 x 10 = 70 cards."`.
2. Proposal B (line 12), same `derivedLineText`, supplies a *wrong* `arithmeticSpec` (bad
   `claimedResult`, or operands that don't actually support B's real claim) → `resolveArithmeticSpec`
   correctly returns `{ ok: false }` for B → nothing is pushed into `composed` for B.
3. When building `claims`, B's `composedFactId` lookup does `composed.find(c => c.claimText ===
   prop.derivedLineText)` — this matches **A's** composed fact, because the search key is text, not
   identity. B is handed A's `composedFactId`.
4. `classifyDerivedLines` (`verify-enumerate.ts:1279-1298`) checks
   `c.claimText !== claim.derivedLineText` — but since A and B share identical text, this check
   passes. B is classified `corroborated-by-composition`, citing A's (unrelated) evidence, even
   though B's own arithmetic was rejected.

This is not caught by any existing test — `verify-derive-check.test.ts`'s composition tests
(lines 853-947) never exercise two proposals with identical `derivedLineText` in the same slice.

**Fix:** Carry the proposal's own identity (index in `derivedLineProposals`, or `lineNumber`)
through the compose-attempt loop and build `composedFactId` from that identity directly instead of
re-deriving it via a text-based `.find()`:

```ts
const composedFactIdByIndex = new Map<number, string>();
reconciler.derivedLineProposals.forEach((prop, i) => {
  if (prop.proposedClassification !== 'corroborated-by-composition' || !prop.arithmeticSpec) return;
  const outcome = resolveArithmeticSpec(prop.arithmeticSpec, prop.derivedLineText, groundedByStatement);
  composeAttempts.push({ lineNumber: prop.lineNumber, outcome });
  if (outcome.ok) {
    composed.push(outcome.composed);
    composedFactIdByIndex.set(i, outcome.composed.id);
  }
});
// later: composedFactId = composedFactIdByIndex.get(i)
```

### CR-03: `findMatch`'s deterministic tie-break can ground two different "both" claims to the same underlying fact when they share a `sourceSentence`

**File:** `src/cli/commands/verify-enumerate.ts:356-392` (`matchRank`/`findMatch`), used by
`validateGrounding` (`:407-448`)

**Issue:** The module's own comment documents that "SEVERAL facts share one `sourceSentence`... a
single rulebook sentence routinely supports multiple facts" (line 353-354) — this is described as
the *normal*, expected case. `findMatch` resolves a reconciler's `quotedFromA`/`quotedFromB` to
*one* `EnumeratedFact` via `matchRank` + a content-derived-id tie-break. If a reconciler quotes the
same full `sourceSentence` for two different "both" claims (entirely plausible: the sentence
genuinely supports both facts, and quoting the whole sentence rather than the specific sub-clause is
not forbidden by `reconcile-facts.md`'s Rule 2), `findMatch(quote, listA)` returns the identical
fact object for both claims — deterministically, since it is a pure function of `(quote, list)`.

Concretely: a sentence "Draw 2 cards and discard 1 card each round." can back two distinct facts in
list A — `{statement: "Draws 2 cards", magnitude: 2}` and `{statement: "Discards 1 card",
magnitude: 1}` — both sharing `sourceSentence` = the full sentence. If the reconciler's claim1
(intended operand = "draws 2") and claim2 (intended operand = "discards 1") both set
`quotedFromA` = the full sentence, both resolve via `findMatch` to whichever of the two facts wins
the rank/id tie-break — the *same one*, for both claims. `GroundedBothFact.matchedFactA` for claim2
then silently carries the wrong magnitude (2, not 1). `extractOperandValue` (verify-enumerate.ts:
538-601) extracts that wrong `numericValue` for arithmetic composition without any way to detect the
mismatch. A `claimedResult` computed from the wrong-but-substituted operand can validate even though
the semantically-correct operand would not have supported it — the exact "wrong claim passes"
failure mode this module's whole design exists to prevent (per its own header comment,
`verify-enumerate.ts:24-30`).

**Fix:** `findMatch` needs to disambiguate among equally-ranked candidates by something more
specific than a global content-id tie-break when multiple facts share a `sourceSentence` — e.g.
prefer the candidate whose `statement` text most specifically matches the *claim's own* `statement`
field (which `validateGrounding` currently ignores entirely for match resolution), or reject
grounding outright when a quote matches more than one fact at the winning rank and the callers can't
disambiguate, surfacing it via `GroundingRejection` instead of silently picking one.

### CR-04: `--slice-path` on `verify-derive-record` has no containment check — arbitrary local file read

**File:** `src/cli/commands/verify-derive-check.ts:1221-1231` (`verifyDeriveRecordCommand`)

**Issue:**

```ts
const slicePath = options.slicePath;
const sliceFsPath = join(projectDir, slicePath);
let sliceText: string;
try {
  sliceText = await fs.readFile(sliceFsPath, 'utf-8');
} ...
```

`join()` collapses `..` segments, so `--slice-path ../../../../etc/passwd` (or any path escaping
`projectDir`) resolves outside the project and is read without complaint. The file's contents then
flow into `sliceText` → `classifyDerivedLines`'s `passages` map → potentially into ledger records
and `--json` stdout output (via absence-claim scanning and error messages that echo `slicePath`).
This module's own header comment claims CHECK-04 is "project-level and source-free by
construction," and the sibling command `verify-classify.ts` already guards its equivalent input:

```ts
// verify-classify.ts:706
`--live-slice "${options.liveSlice}" resolves outside ${relative(projectDir, rulebookDir)}.\n`
```

`verify-derive-record`'s `--slice-path` has no equivalent guard, despite reading the file at that
path directly off disk. In the normal orchestrated flow `--slice-path` is supplied by the skill
orchestrator using `verify-derive-check`'s own reported paths (trusted), but the CLI itself performs
no validation — a malformed/compromised invocation (or a future caller of this exported function)
gets arbitrary local file read with no containment boundary, silently inconsistent with the
established convention elsewhere in this same milestone.

**Fix:** Mirror `verify-classify.ts`'s guard — resolve `sliceFsPath` and reject when it does not
stay within `join(projectDir, 'rulebook')`:

```ts
const rulebookDir = join(projectDir, 'rulebook');
const sliceFsPath = resolve(rulebookDir, slicePath);
if (!sliceFsPath.startsWith(rulebookDir + sep)) {
  throw new Error(
    `--slice-path "${slicePath}" resolves outside ${relative(projectDir, rulebookDir)}.\n` +
      `Pass a path relative to rulebook/.`,
  );
}
```

## Warnings

### WR-01: `verify-derive-check.ts` bundles four distinct responsibilities into one 1290-line file

**File:** `src/cli/commands/verify-derive-check.ts`

**Issue:** The file now mixes (1) live-tree reading + candidate enumeration, (2) the project-level
ledger's validate/read/write machinery, (3) the read/report CLI command
(`verifyDeriveCheckCommand`), and (4) the compute pipeline + write CLI command (`reconcileSlice`,
`verifyDeriveRecordCommand`). The plan-checker flagged this file as a likely split candidate before
the phase closed; at 1290 lines with four independently-testable concerns, the accumulated size is
exactly what made CR-02 above (a subtle text-keyed lookup bug 30 lines away from where `composed` is
built) easy to introduce and easy to miss in review — the compute pipeline's correctness-critical
logic is buried among ledger I/O and CLI-formatting code that has nothing to do with it.

**Fix:** Split along the existing section-comment boundaries: `derive-check-slices.ts` (readLiveSlices/
annotationBody/quoteLinesOnly/enumerateDerivedLines), `derive-check-ledger.ts`
(createDeriveCheckRecord/replace/record/read), and keep `reconcileSlice` + the two CLI commands in
`verify-derive-check.ts`. Each becomes independently reviewable and testable.

### WR-02: The `verify-enumerate.ts` ↔ `verify-derive-check.ts` import cycle is safe only by an unenforced convention

**File:** `src/cli/commands/verify-enumerate.ts:5`, `src/cli/commands/verify-derive-check.ts:7-30`

**Issue:** The cycle is genuinely safe today — `quoteLinesOnly` (imported by `verify-enumerate.ts`)
is only invoked inside function bodies (`buildEnumeratorPayload`, the absence-check branch of
`classifyDerivedLines`), never at top-level module-init time, and the reverse imports into
`verify-derive-check.ts` are likewise all function-body uses or type-only. Native ESM live bindings
make this safe as long as that invariant holds. But nothing enforces it: no lint rule, no
architecture test, no comment-adjacent guard prevents a future contributor from adding, say, a
top-level `const DEFAULT_PAYLOAD = buildEnumeratorPayload(...)` to either file, which would silently
reintroduce a TDZ/`undefined`-at-init hazard exactly of the kind `derived-line-pattern.ts`'s own
header comment (lines 11-17) warns about for a *different* cycle in this same codebase.

**Fix:** Add a `derived-line-pattern.test.ts`-style pinned regression test that imports both modules
fresh (e.g. via dynamic `import()` in a dedicated test) and asserts every cross-cycle export is
defined and callable, or add an eslint import-cycle rule scoped to these two files with an inline
suppression comment explaining why it's accepted, so a future violation fails loudly instead of
silently.

### WR-03: `ANNOTATION_CITATION_SOURCES` is exported but has no consumer

**File:** `src/cli/commands/derived-line-pattern.ts:101-114`

**Issue:** `ANNOTATION_CITATION_SOURCES` is documented as "offered for a future consumer that needs
the family list in that exact shape," but `verify-classify.ts`'s comment (referenced from this same
file's own comment) explicitly says it does *not* use it and keeps its own separate literal. Nothing
else in `src/` imports it. This is speculative/YAGNI surface area shipped without a consumer.

**Fix:** Either delete it until a real consumer exists, or leave it — low priority — but do not add
further speculative exports of this shape without a concrete near-term consumer.
