# v4.9 Milestone Audit — BS Skills Re-Verification

## Verdict

**tech_debt.** All 25 requirements are closed on real, cited, live evidence — not on assertion, not
on synthetic-only data, and (with one new exception below) not on a mechanism the user's own path
can't reach. This is a genuinely rigorous milestone: it caught and fixed three real instances of its
own core failure mode (closed-but-unreachable) mid-milestone, retired a miscalibrated metric instead
of quietly declaring victory, and self-disclosed a corrected-after-the-fact overclaim (§10 of
178-PROOF.md) about full-tree cleanliness. None of that is praise-padding — it's why the milestone is
close to a clean pass rather than a re-open. It is not a clean pass because: (1) the ROADMAP's own
Phase 170 bookkeeping is internally contradictory in a way that would mislead a future reader, and (2)
this audit found a fourth, undisclosed instance of the milestone's own named failure pattern
(reachability) in Phase 178, structurally identical to one Phase 177.1 disclosed and fixed but never
checked against Phase 178's later, similar proof. Neither finding invalidates the requirement closures
themselves — the underlying mechanisms are real and were exercised with live model dispatches — but
both should be fixed or explicitly accepted before this milestone is archived as done.

## The Phase 170 lead — investigated, disposition: legitimate, but under-documented

**PROC-01, PROC-02, INGEST-01 through INGEST-04 were closed on real evidence — via `170-10`, not via
the individually-scoped `170-08`/`170-09` the ROADMAP still lists as unchecked.**

- `170-08-PLAN.md` ("dispatch prompt as template + per-slice line-kind receipt; INGEST-02 on live
  output") and `170-09-PLAN.md` ("capture passing-run evidence + PROC-02 adversarial closure") have
  no `-SUMMARY.md` files and are unchecked `[ ]` in `ROADMAP.md`. That part of the lead is accurate.
- But `170-MECHANISMS.md` (written mid-phase, after 12 failed attempts to make skill text convey
  mechanical instructions) explicitly states `170-08`'s mechanism was **executed, then refuted** —
  its `## Line-kind receipt` block and invented-heading rule were built, tried, and found not to
  survive a real run, so they were dropped rather than shipped. `170-09`'s scope (capture evidence +
  adversarial PROC-02 closure) was never run standalone; it was absorbed into `170-10`.
- `170-10-PLAN.md` **does** have a `-SUMMARY.md` (`170-10-SUMMARY.md`, dated 2026-07-28) and **is**
  the real closure: two full human-driven `/bs-ingest-rules` runs against a real rulebook. **Run 1
  failed 3 of 9 acceptance items** (reconciliation count mismatch, zero `Visual` lines, a card-art
  line mis-filed as `Derived`) — a real, adversarial, non-trivial failure, not a rubber stamp. The
  root cause (`boardsmith init`'s pre-commit hook never fires because `/bs-ingest-rules` contains no
  commit) was diagnosed and fixed (`92f88bb9`, `c32bc184`: machine-owned fenced gaps section,
  `boardsmith ingest-check` repair-then-fail gate, extended derived-purity lexicon). **Run 2, against
  the fix, passed all 9 items** on the as-left tree, with the session explicitly declining to
  hand-tidy the machine-owned section it could tell was imperfect — real judgment behavior, not a
  scripted pass. `170-10-SUMMARY.md`'s own text records the requirement closures explicitly: "PROC-01,
  PROC-02, INGEST-01, INGEST-02, INGEST-03, INGEST-04 — marked Complete in `REQUIREMENTS.md`."
- INGEST-02 specifically (`Visual`/`Derived` separability) is directly evidenced in Run 2's item (h):
  "Visual=3, Derived=12" — real, live-transcribed output, not the harness's synthetic fixtures.
- `REQUIREMENTS.md`'s PROC-01 note cites Phase 173 evidence (`173-PROOF.md` §§3-4) rather than
  `170-10`. Both are legitimate, independent evidence for the same requirement — not a conflict.

**Disposition: legitimate substitution, real evidence, correctly closed.** The failure mode this audit
was primed to find (bare checkboxes / closed-on-nothing) did not occur here. What's wrong is
bookkeeping: `ROADMAP.md` still shows Phase 170 as `[x]` complete at the top of the Phases list, its
own plan checklist still shows `170-08`/`170-09`/`170-10` all unchecked `[ ]`, and the Progress table
at the bottom of `ROADMAP.md` (line ~499) reads **"170. Ingest Contract Upgrade | 5/10 | In Progress"**
— three mutually contradictory statements about the same phase in the same file. A reader trusting the
Progress table alone would conclude Phase 170 is half-done; it is not. **Fix before archive:** check
`170-10` (and, if desired, mark `170-08`/`170-09` superseded rather than pending), and correct the
Progress table row to `10/10 Complete`. Same staleness affects the Phase 174 and Phase 177 Progress
rows, which still read "Reopened — goal NOT MET" / "Executed — goal NOT MET" despite both being
`[x]` complete with later Results recording MET-under-the-stated-bar (174) and CLOSED (177) —
technically accurate as history but stale as a status field a future reader would scan first.

## New finding: a fourth reachability instance (Phase 178, undisclosed)

The prompt named three known instances of this milestone's recurring failure mode — closing a
requirement on evidence produced by something other than the path a real user/session takes:

1. CHECK-04 → closed on a `.planning/` harness; fixed by Phase 177.1 (real CLI + skill wiring built).
2. Phase 178's SC-3 (shared derivation module) → proven by source inspection, correctly labeled as
   such, never smoothed into a dispatch claim. Not a gap — honestly scoped.
3. PROV-02 → closed on the build pipeline only; fixed by Phase 179 (wired into the verify pipeline).

**A fourth instance exists, in Phase 178's CHECK-06/TEST-01 closure, and it is not disclosed the way
the other three were.**

`178-PROOF.md` (the live proof both CHECK-06 and TEST-01 cite for closure) drove the
extract→translate→emit→execute pipeline via **direct `claude -p` dispatch calls issued by the proof's
own harness script**, carrying the real contract files (`extract-example.md`/`translate-example.md`)
and the real CLI commands. It never invoked `/bs-verify-game` or `/bs-build-chunk` as an actual
interactive orchestrator session reading `verify-game.md` Step 8 / `build/test.md` item 4 and choosing,
turn by turn, to dispatch the right subagent at the right point in the right order. Nowhere in
`178-PROOF.md` is this limitation named.

Compare `177.1-08` (the CHECK-04 reachability fix's own live proof), which hit the identical
constraint — its executor session also had no Task tool — and **disclosed it explicitly**:

> "The plan's `<interfaces>` section specifies dispatch via the Task tool... in PRODUCTION the
> `/bs-verify-game` orchestrator runs inside an interactive Claude Code session that has Task-tool
> subagent dispatch available. This executor session's own tool surface... does not expose a
> Task/subagent-dispatch tool... `claude -p` was used as the closest available faithful proxy...
> What is NOT reproduced here is the Task-tool's own subagent sandboxing/context-isolation
> mechanics — a genuine gap between this proof and what a designer's live Claude Code session
> would do."

This distinction matters specifically *in this milestone*, because Phase 170's own foundational
finding — the one that reshaped the rest of the roadmap — is that **BoardSmith's orchestrator
"reliably fails to convey mechanical work"**: it composes subagent prompts from memory rather than
the file it just read, it bypasses fan-out and does work inline, and it skips newly-added mechanical
steps even from a just-read file (`170-MECHANISMS.md`, "The three observations that cracked it").
CHECK-06 (`verify-game.md` Step 8) and TEST-01 (`build/test.md` item 4) are exactly the shape of
requirement Phase 170 warned about: a multi-step mechanical sequence (enumerate pending slices →
dispatch extraction → dispatch translation → record → emit → execute → route the verdict) that a real
orchestrator session must follow correctly, unprompted by any error message, for the feature to work
at all. Neither `178-PROOF.md` nor `179-PROOF.md`'s CHECK-06 dispatch (also a scripted loop, not a
live `/bs-verify-game` session) tested that specific risk — and only one of the milestone's two
closures involving this exact proxy-dispatch technique disclosed it as a limitation.

**This is a documentation-honesty gap, not a demonstrated functional failure.** The underlying
commands, ledger, and contracts are real, tested, and were exercised with genuine live model calls
(real defects were found and fixed mid-proof — the import-hoisting bug and the payload-depth bug in
§0 of `178-PROOF.md` are exactly the kind of thing a "proof that only exercises what already works"
would have missed). But given this milestone's own governance standard — established by name in
`170-MECHANISMS.md` and reinforced by fixing three other instances of the same class of gap — this
one should have been named the way `177.1-08` named it, and wasn't.

**Recommendation:** before archiving, either (a) run one real interactive `/bs-verify-game` (or
`/bs-build-chunk`) session against a staged reference-game copy to close the actual gap, or (b) add an
explicit disclosure to `178-PROOF.md`/`REQUIREMENTS.md`'s CHECK-06/TEST-01 entries naming this as a
known, accepted limitation — consistent with how `177.1-08` handled the identical constraint. Either
is a small amount of work; leaving it silently undisclosed is the one thing inconsistent with how the
rest of this milestone operates.
