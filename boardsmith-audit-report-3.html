CRITICAL F1. Zone visibility (contentsHidden/contentsVisibleToOwner) is silently lost on every snapshot restore — hidden hands leak to all players
src/engine/element/space.ts:114 engine-elements

The trap (wrong way is easy)

The docs, Space docstring, and every example game (go-fish game.ts:56-64, cribbage game.ts:167-189) model configuring hidden information via zone visibility in the game constructor: `deck.contentsHidden(); hand.contentsVisibleToOwner()`. But `_zoneVisibility` is a `_`-prefixed private field listed in `Space.unserializableAttributes` (space.ts:114-118), so `toJSON()` never emits it — and `Game.loadSerializedState` (game.ts:2848-2857) discards the constructor-built tree (`this._t.children = []`) and rebuilds every Space via `fromJSON`, which never restores zone visibility. Proven end-to-end: after `GameRunner.fromSnapshot` (the documented 'SINGLE sanctioned way' to restore checkpoints, used by undo and server restore), `game.toJSONForPlayer(opponent)` for a `contentsVisibleToOwner()` hand went from `{"__hidden":true}` placeholders to the full card identity (`{"name":"secret","rank":"A"}`). One undo or server restart and every opponent hand and deck order is broadcast in cleartext.

The right way (and why it's hard)

There is no right way today short of the developer knowing to re-apply zone visibility after every restore (no hook exists for this) or using only per-element `_visibility` (piece.hideFromAll()/showOnlyTo()), which IS serialized (game-element.ts:794 emits `json.visibility` when explicit). Nothing in the API or docs distinguishes the durable per-element mechanism from the volatile zone mechanism — they look equivalent and the zone one is the one the docs teach.

Suggested fix

Serialize `_zoneVisibility` (it's plain data — mode + player lists) in Space's toJSON/fromJSON exactly like element-level `_visibility` already is, and add a round-trip test asserting `toJSONForPlayer(opponent)` is identical before/after `GameRunner.fromSnapshot`. The SEC-02 hidden-attrs regression sweep should also run against a restored game, not only a live one.

Verifier verdict

Confirmed by direct code reading and an executable repro; I could not refute it. (1) Mechanism verified: `_zoneVisibility` is in `Space.unserializableAttributes` (src/engine/element/space.ts:114-118) so `toJSON()` never emits it; only per-element explicit `_visibility` is serialized (src/engine/element/game-element.ts:793-795). `Game.loadSerializedState` (src/engine/element/game.ts:2848+) does `this._t.children = []` and rebuilds every Space via `GameElement.fromJSON`, so the constructor-applied zone visibility is discarded and never restored. `GameRunner.fromSnapshot` (src/runtime/runner.ts:535-600) calls exactly this, and `GameSession.restore` (src/session/game-session.ts:785) and the undo/rewind checkpoint paths (stateless-ops runnerFromSnapshot/runnerFromCheckpoint) all go through it with no re-application of zone visibility. (2) Empirically reproduced: a minimal vitest game with `hand.contentsVisibleToOwner()` shows opponent `toJSONForPlayer(2)` leak = false before snapshot restore, true after `GameRunner.fromSnapshot` (test failed on the after-restore assertion). (3) The codebase itself admits the hazard: src/session/stateless-ops.ts:218-222 says the spectator view MUST be built from the LIVE runner because "zone visibility ... is NOT serialized, so a fromSnapshot reconstruction would lose it and over-reveal" — a spot workaround for one sub-path, with no guard on the general restore/undo paths. (4) It is squarely the easy path: docs, the Space docstring example (space.ts:36-50), go-fish, and even BoardSmith's own runner.test.ts fixture game all use `contentsHidden()`/`contentsVisibleToOwner()` in the constructor as the canonical hidden-information mechanism. No lint rule, type, or doc warns that zone visibility is volatile across restore. A reasonable developer following the documented pattern gets hidden hands and deck order broadcast to all players after any undo or server restart, silently. Hidden-information integrity is the core trust property of a board-game engine, so critical severity stands.

HIGH F3. eachPlayer startingPlayer silently skips players (no wrap-around) — and the docs model the broken dealer pattern
src/engine/flow/engine.ts:1116 engine-actions-flow

The trap (wrong way is easy)

In board games, 'start the round from the player left of the dealer' universally means wrap-around rotation. A dev writes eachPlayer({ startingPlayer: () => game.playerAfterDealer, do: ... }) — exactly what docs/common-patterns.md:54 shows as the canonical dealer-rotation pattern, and what TurnOrder.LEFT_OF_DEALER / START_FROM / CONTINUE (src/engine/flow/turn-order.ts:50,82,131) encode as named presets. But executeEachPlayer builds eligibleSeats via players.slice(startIndex) with no wrap, so every player seated BEFORE the starting player is silently skipped that round. With 4 players and dealer at seat 3, only seat 4 gets a turn. Nothing errors; the round just quietly loses players, and the bug moves around as the dealer rotates.

The right way (and why it's hard)

The correct usage is to not use startingPlayer for round-robin at all and instead restructure the flow to handle wrap-around manually (the only hint is a note buried in turn-order.ts JSDoc: 'it does NOT wrap around'). There is no wrapping variant offered, so the right way requires reading engine internals and hand-rolling seat math, while the wrong way is a named preset literally called LEFT_OF_DEALER and the project's own common-patterns doc.

Suggested fix

Make wrap-around the default: eligibleSeats = [...players.slice(startIndex), ...players.slice(0, startIndex)]. If truncation is ever genuinely wanted, make it an explicit opt-in (e.g. wrap: false). Fix docs/common-patterns.md and the TurnOrder preset docs to match. At minimum, dev-warn when startingPlayer excludes seats.

Verifier verdict

Confirmed in code: engine.ts:1116 builds eligibleSeats via players.slice(startIndex) with no wrap-around, so every player seated before startingPlayer is silently skipped that round. docs/common-patterns.md:54 (the FIRST pattern in the guide, 'Dealer Rotation') models exactly this broken usage with no caveat, and docs/actions-and-flow.md:906 shows TurnOrder.LEFT_OF_DEALER the same way. The trap is amplified by inconsistent semantics: game.nextAfter() (used by the doc's playerAfterDealer) is explicitly circular, while eachPlayer iteration is not. The only warnings live in turn-order.ts JSDoc, not the docs developers read. No guardrails exist: no eslint rule covers it, no tests exercise startingPlayer, and no example game or MERC uses startingPlayer/TurnOrder at all — meaning there's no correct exemplar either. A reasonable developer following the project's own canonical pattern hits silent wrong behavior. HIGH F4. Failed action in simultaneousActionStep is reported as success and recorded in actionHistory
src/engine/flow/engine.ts:457 engine-actions-flow

The trap (wrong way is easy)

During a simultaneousActionStep (e.g. everyone discards down to 4 cards), a player submits an invalid selection or execute() throws. resumeSimultaneousAction does `if (!result.success) return this.getState();` WITHOUT setting this.actionError — unlike the regular resume path (line 267) which records it. GameRunner.performAction (src/runtime/runner.ts:207) detects failure only via flowState.actionError, so it sees none, returns success:true, and pushes the never-executed action into actionHistory. The client is told the action succeeded, the UI advances, and the replay/undo history now contains an action that never mutated state — replays and snapshots silently diverge.

The right way (and why it's hard)

There is no right way from the game dev's side — this is an engine bug in the less-traveled simultaneous path. The regular action-step path handles failure correctly, so devs testing single-player turns will never see it; it only corrupts state in multi-player concurrent phases, which are the hardest to test.

Suggested fix

In resumeSimultaneousAction, mirror the regular path: set this.actionError = result.error before returning getState(), and clear it on success. Add an engine test that a failed simultaneous action surfaces actionError and is NOT recorded in actionHistory.

Verifier verdict

CONFIRMED by live reproduction, not just code reading. I built a minimal SimGame whose 'ready' action throws in execute() during a simultaneousActionStep, drove it through GameRunner.performAction (the exact object GameSession.#runner uses at game-session.ts:1303), and observed: execute() threw, no state mutated, yet the runner returned success:true and pushed the never-executed action into actionHistory. Mechanism verified at each layer: (1) ActionExecutor.executeAction (src/engine/action/action.ts:970-979) catches thrown execute() errors and returns {success:false} — so GameRunner's try/catch around continueFlow never fires; (2) FlowEngine.resumeSimultaneousAction (src/engine/flow/engine.ts:457-459) does `if (!result.success) return this.getState();` without setting this.actionError, unlike both sibling paths resume() (line 268) and resumeAfterExternalAction() (line 298) which set it; (3) GameRunner.performAction (src/runtime/runner.ts:207) detects failure solely via flowState.actionError, so it records the action (line 217) and returns success:true. No guardrail exists: nothing in the session layer re-validates, no eslint rule applies (this is engine code, not game code), and there is zero test coverage for a failing action in a simultaneous step (the only failure-adjacent sim test in engine.test.ts covers a 'missing' action name, which throws and IS caught by the runner). The claim's Pit-of-Success framing is accurate: a game dev cannot avoid this — the well-trodden sequential path handles failure correctly, so single-player testing shows nothing wrong; only the hard-to-test concurrent path lies. Severity adjusted from critical to high: the failed action deterministically no-ops on replay too (resumeSimultaneousAction returns before playerDone/completion checks), so snapshots/replays converge rather than diverge as claimed; the concrete harms are the client being told success while server state is unchanged (silent swallowed error, seat still awaiting), polluted actionHistory corrupting undo counting (undo pops a no-op instead of the player's real last move), and per-action checkpoints keyed to inflated history length. Real engine bug, straightforward one-line fix (set this.actionError = result.error in the sim path).

The trap (wrong way is easy)

`moveToInternal` does no self/descendant check. In `moveToInternal`, walk `destination._t.parent` up to the root; if `this` is encountered (or `destination === this`), throw an actionable error ('Cannot move X into its own descendant Y'). The walk is O(depth) and matches the fail-fast-and-loud rule.

Serialize `_zoneVisibility` in `Space.toJSON()` and restore it in `GameElement.fromJSON` (it is a small plain object, exactly like the already-serialized element `_visibility`/`json.visibility`). That makes every fromSnapshot path — undo, rewind, restore, stateless ops — visibility-faithful, and makes runtime visibility changes (cribbage crib reveal/re-hide) survive too.
